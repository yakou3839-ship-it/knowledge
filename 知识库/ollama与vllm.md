## KV缓存（Key-Value Cache，KV 缓存）

### 一、一句话定义

**KV Cache 是大模型（GPT/LLaMA 等自回归 Transformer 推理）最核心的加速技术**：

在逐 Token 生成文本时，**缓存历史所有 Token 计算出来的 Key、Value 向量**；后续生成新 Token 直接复用缓存，不用反复重算历史 K/V，大幅减少算力开销。、

> 只缓存 K、V，**不缓存 Query (Q)**。

### 二、前置背景：自回归生成痛点

大模型对话是**逐字生成（自回归 Decode）**：

输入 Prompt → 生成第 1 个 token

输入 Prompt + 第 1 个 token → 生成第 2 个 token

输入 Prompt + 前 2 个 token → 生成第 3 个 token……

**无 KV Cache（原生方式）**

每生成 1 个新词，**把全部上下文从头计算一遍 Q/K/V**。

假设上下文长度为 n，单次注意力复杂度 \(O(n^2)\)。序列越长，计算爆炸，完全无法实用。

**有 KV Cache**

历史 Token 的 K、V 一旦算完就固定不变，可以存起来；

每次只**计算最新单个 Token 的 Q、K、V**，拿新 Q 和缓存里全部历史 K/V 做注意力计算，再把新 K/V 追加进缓存。复杂度降低为 \(O(n)\)。

### 三、两个阶段完整流程

**1. Prefill 预填充阶段（首次处理输入 Prompt）**

用户提问一次性送入模型，并行计算 Prompt 内所有 token 的 Q/K/V；

把所有 K、V 存入 KV 缓存。

✅ 耗时比较长（大批量并行计算），**流式输出刚开始的延迟主要来自 Prefill**。

**2. Decode 解码阶段（逐个生成回答 token）**

循环执行：

1. 输入上一轮生成的 1 个 token；
2. 仅计算这个新 token 的 \(Q_{new},K_{new},V_{new}\)；
3. 注意力计算：\(Attention(Q_{new},\;K_{缓存}+K_{new},\;V_{缓存}+V_{new})\)
4. 将 \(K_{new},V_{new}\) **追加写入 KV 缓存**；
5. 输出下一个 token，继续循环。

```
Step1(token1): 算Q1,K1,V1 → 缓存[K1,V1]
Step2(token2): 算Q2 → 使用缓存K1V1 → 缓存追加[K2,V2]
Step3(token3): 算Q3 → 使用缓存K1K2,V1V2 → 缓存追加[K3,V3]
```

### 四、高频面试核心问题

**1. 为什么只缓存 K、V，不缓存 Q？**

- **Key / Value：属于历史上下文，后续每一轮都会反复被查询，永久复用**

- Query：只代表「当前这一步要查询的内容」，本轮用完立刻失效，下一轮 Query 完全不一样

  缓存 Q 只会白白占用显存，没有收益。

**2. KV Cache 存在哪里？**

存于 **GPU 显存（HBM）**。

⚠️ 重要现实问题：

**KV 缓存是显存头号消耗大户！**

长对话场景下，KV 占用显存经常**超过模型权重本身**；上下文越长，缓存体积线性上涨。

线上服务能同时承载多少并发请求，瓶颈几乎都是 KV 缓存显存，不是模型权重。

**3. 训练阶段需要 KV Cache 吗？**

**不需要！**

训练时所有 Token 并行一次性计算，不存在逐一生成，没有重复计算，因此训练框架默认关闭 KV 缓存。

KV Cache**只用于推理（Inference）**。

### 五、KV Cache 带来的权衡

✅ 优点

1. Decode 阶段速度提升几倍～几十倍，是流式对话必备；
2. 消除大量冗余矩阵运算。

❌ 代价（空间换时间）

1. 持续占用大量 GPU 显存；
2. 序列越长，缓存越大；长文本极易 OOM 显存溢出；
3. 多用户并发场景容易产生显存碎片。

### 六、常见配套优化（工程部署必会）

针对 KV 缓存显存难题，主流优化方案：

1. PagedAttention（vLLM/SGLang 核心）

   分页式 KV 缓存，类似操作系统虚拟内存，解决显存碎片，大幅提升并发吞吐。

2. KV 量化：FP16→FP8 / INT4，降低缓存显存占用；

3. KV Cache 淘汰（eviction）：丢掉不重要的早期 token，支撑超长上下文；

4. MLA（DeepSeek）：压缩 KV 向量长度，原生降低缓存大小；

   - 从v2版本后面都是MLA（多头潜在注意力）

5. KV Offloading：把冷 KV 缓存交换到 CPU 内存，释放 GPU 显存。

### 七、冷KV与热KV

#### **基础定义（KV 缓存分层存储概念，和 MLA 无关，所有模型通用）**

一条长对话的 KV 缓存，按**访问频率、时效性**划分：

#### 🔥 Hot KV（热 KV）

**当前正在生成 token、高频被注意力访问的 KV 块（最近一批 token）**

- 存放位置：**GPU HBM 显存**
- 例子：对话末尾最新几百个 token；正在 decode 生成回答的上下文
- 特征：每一步解码一定会读取，延迟要求极高，绝对不能挪走

#### ❄️ Cold KV（冷 KV）

**历史久远、极少被模型访问的早期上下文 KV 缓存**

- 存放位置：**CPU 内存 / NVMe 磁盘（KV Offloading 卸载）**
- 例子：一段 128K 长文档最开头几千 token；多轮对话最早的历史 prompt
- 特征：绝大多数解码步骤不会读到；只有模型回头检索前文时才需要加载

#### 可选：温 KV（Warm KV，工程常用中间态）

既不极端活跃、也不完全闲置，一般放在 CPU 内存，介于冷热之间。

#### 通俗比喻

你在读一本长篇小说（上下文序列），一边读一边续写（自回归生成）

- **热 KV**：你眼前刚读完的几页，一直摊在桌面（GPU 显存），随时翻看；

- 冷 KV

  ：书本最前面几十页，很久不会回看；收进书柜（内存 / 硬盘）；

  

  只有需要回溯查阅的时候，才临时拿出来放到桌面。

#### 工程里如何利用冷热 KV（KV Offloading）

GPU 显存昂贵有限，无法放下超长序列全部 KV：

1. 策略：**只把热 KV 留在 GPU；冷 KV 卸载到 CPU 内存 / SSD**

2. 当模型注意力突然命中古老前文（访问冷 KV）：

   触发提升 (Promote)：把冷 KV 从内存 / 磁盘传回 GPU 显存，临时变成热 KV；

3. 代价：冷 KV 访问会引入 PCIe 传输延迟，造成少量 token 卡顿。

#### 额外补充：和「KV 缓存淘汰（Eviction）」区别

- Offloading 冷热迁移：**数据保留，只是挪到低速存储**，需要时取回

- Eviction 淘汰：直接永久删除旧 KV，无法恢复（典型：vLLM 长上下文滑动窗口）

  > Eviction = 永久删除一部分 Token 对应的 K/V 向量，直接释放显存。一旦淘汰，数据彻底消失；后续如果模型需要这段上下文，只能重新跑 Prefill 计算 K/V。
  >
  > 什么时候会触发Eviction
  >
  > - 场景 1：单条超长对话内部缓存压缩（序列内淘汰）
  >
  >   - **StreamingLLM（滑动窗口 + Attention Sink）**
  >
  >     保留最开头少量`sink token`（注意力汇，必须留，防止模型崩溃）+ 最近 N 个 token；更早历史全部淘汰。长流式对话最常用。
  >
  >   - **H2O Heavy-Hitter Oracle**
  >
  >     统计历史注意力分数，淘汰长期得不到注意力、不重要的 token，保留高频被关注的 token。
  >
  > - 场景 2：推理引擎调度抢占（请求级驱逐，vLLM 等框架）
  >
  >   > GPU 显存满载，新请求进不来。调度器选择**低优先级会话，把整条请求所有 KV 全部 Evict（丢弃）**，腾出显存给新请求。
  >
  >   - 模式 A：**Swap（Offload 交换）**：KV 搬到 CPU 内存，后续可以恢复继续生成
  >   - 模式 B：**Recompute（Eviction 硬淘汰）**：直接删除 KV；等资源空闲后，整条对话从头重新 Prefill
  >
  >   > vLLM V1 默认不再推荐 swap，默认采用 recompute eviction，减少 CPU 内存占用。
