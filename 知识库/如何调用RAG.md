# 完整流程：大模型怎么判断「要不要查知识库」+ 怎么检索

先纠正一个常见错觉：

**大模型本身不会 “主动知道” 要去查向量库。整套检索是【外部程序控制】的，不是大模型大脑自发行为。**

这套架构标准名字：**RAG（检索增强生成 Retrieval-Augmented Generation）**

我分成两大块讲清楚：

1. 系统如何判断：**这个问题需不需要检索知识库？**
2. 如果判定需要：**向量检索完整执行链路**
3. 最后举极简时序案例，顺带讲主流两种实现方案

> 基础架构组成：用户输入 → 调度程序（RAG 框架：LangChain/LangGraph/Dify/Coze）→【检索判断模块】→ 向量数据库 → 把检索文本 + 问题一起喂给大模型 → LLM 输出答案

## 一、核心关键点（重中之重）

大模型原生没有能力主动调用向量库！

**是外层代码（RAG 框架）决定是否检索，大模型只是被调用的组件。**

有两种工程实现路线，业界都在用：

## 方案 A：简单粗暴模式（很多新手、简易 RAG 系统默认）

✅ **不做判断！任何用户提问，一律强制检索向量库**

流程：

用户问句 → 直接向向量库检索 Top-K 相关文档 → 把【检索片段 + 用户问题】拼接成 Prompt 丢给大模型

提示词示例：

plaintext







```
参考资料：{检索到的文本}
基于上面资料回答用户问题：{query}
如果资料没有相关信息，可以凭你原有知识回答
```

### 优缺点

优点：实现最简单；不会漏查知识库内容

缺点：

1. 很多无关问题（你好、闲聊、计算、逻辑题）也去查库，浪费算力、增加延迟
2. 无关文档混入上下文，干扰大模型回答（噪声）

## 方案 B：智能判断模式（生产级 RAG 标准做法）

先让模型判断：**当前问题是否依赖私有知识库，是否需要检索**

这里又分两种实现方式：

### 方式 1：LLM 分类判断（最常用）

外层代码先把用户问题单独发给大模型，下发一条**分类 Prompt**

示例 Prompt：

plaintext







```
任务：判断用户的问题是否需要查询内部知识库才能回答
规则：
1. 问题询问公司业务、项目文档、私有资料 → 输出：SEARCH
2. 闲聊、通用常识、数学计算、开放性创意问题 → 输出：NO_SEARCH
只允许输出 SEARCH 或者 NO_SEARCH，不要多余文字
用户问题：{用户query}
```

大模型返回 `SEARCH` → 程序触发向量检索

大模型返回 `NO_SEARCH` → **直接跳过检索，直接回答**

### 方式 2：关键词 / 规则判断（轻量，不用调用 LLM）

不调用大模型，代码层面正则、关键词匹配：

比如知识库是【公司内部接口文档】

只要问题包含：接口、请求参数、返回体、部署地址，就触发检索。

缺点：规则覆盖不全，复杂问句识别差。

> 市面上 Dify、FastGPT、LangGraph 都同时支持「强制检索」和「LLM 路由判断」两种模式，可以开关。

------

# 二、一旦确定【需要检索】，向量知识库完整检索步骤

## 步骤 1：Query 改写（可选优化环节，工业常用）

原始用户问句：`系统登录报错怎么办？`

直接拿去检索效果一般，程序可以让 LLM**生成多个检索 Query**：

1. 系统登录失败解决方案

2. 登录页面异常常见原因

3. 账号登录报错排查方法

   

   目的：多角度检索，提高召回相关文档

## 步骤 2：向量化（Embedding 嵌入）

调用**Embedding 模型（文本嵌入模型，≠对话大模型）**

把人类文字问句 → 转换成一串浮点数数组 = **向量（Embedding）**

例：`[0.123,0.456,-0.221,...]`

> 注意：存入知识库的文档，当初也是用**同一个 Embedding 模型**向量化！
>
> 不同模型生成的向量空间不通用！

## 步骤 3：向量数据库相似度检索

把问句向量送入向量库（Milvus、Chroma、FAISS、Qdrant）

向量库内部做：**相似度计算（余弦距离 / 欧氏距离）**

逻辑：

向量越接近 → 文本语义越相似

比如：

用户问题向量 ≈ 文档《登录故障排查》向量 → 高分匹配

检索结果：返回相似度最高的前 K 条文本片段（Top-K，通常 k=3~8）

这一步只看语义，不理解文字含义，纯数值计算！

❗向量数据库**不懂语义，只会算向量距离**，经常出现：字面不一样，但语义相近被召回；或者字面相似语义无关（向量漂移问题）。

## 步骤 4：重排序 Rerank（生产环境标配优化，可选）

向量检索只粗筛，容易混入无关内容。

把召回的文档 + 用户问题送入 Rerank 模型，重新打分，过滤低相关文本。

减少无用材料进入 Prompt，防止幻觉。

## 步骤 5：构造最终 Prompt，送入对话大模型

把筛选后的知识库文本片段 + 用户原始问题拼接，组成提示词发给 LLM

标准 Prompt 模板：

plaintext







```
下面是可供参考的文档资料：
{文档片段1}
{文档片段2}

要求：优先使用参考资料内容回答用户问题，
如果资料没有相关信息，再使用你的通用知识，不要编造不存在信息。
用户提问：{query}
```

## 步骤 6：大模型生成答案返回用户

大模型读取上下文里的参考资料，组织语言输出。

# 三、完整端到端时序示例（直观串起来）

假设私有知识库存放【内部接口文档】

用户输入：`上传文件接口支持什么格式？`

1. RAG 框架把问题发给 LLM 做路由判断

   

   Prompt 判断：该问题属于内部接口文档 → 返回 SEARCH

2. 触发检索流程

3. embedding 模型将问句转为向量

4. Milvus 向量库检索，找到《文件上传接口说明》文档片段

5. Rerank 过滤无关结果

6. 拼接文档片段 + 问题构造 prompt

7. 将完整 prompt 发给对话大模型

8. 模型基于文档回答并返回用户

另一个例子：用户输入 `1+2等于几`

1. 路由 LLM 判断：通用数学问题，不需要查私有知识库 → NO_SEARCH
2. 直接跳过向量检索，直接丢问题给大模型回答

# 四、高频疑问解答

## Q1：向量库里存的是原始文档吗？

不是。原始长文档会预先**文本分割（Chunk 分片）**

比如一份 10000 字文档，切成每 300~800 字一小块；

每一块文本单独生成向量存入向量库。检索也是召回碎片，不是整篇文档。

## Q2：能不能让大模型自己决定什么时候调用知识库（Function Calling 工具调用）？

✅可以！这是更高级方案：**Agent + 工具调用**

原理：

给大模型提供工具描述：

> 工具名称：knowledge_search
>
> 功能：查询内部文档，获取业务相关资料

大模型自主思考：我现有知识无法回答 → 输出工具调用指令

外层程序捕获调用指令 → 执行向量检索 → 把检索结果再次传给大模型继续生成。

区别对比：

1. LLM 路由判断（普通 RAG）：一次判断，串行流程，简单稳定；

2. Function Calling Agent：大模型自主决策，可以多轮多次检索，适合复杂多步骤问题；

   

   市面上智能客服、AI 助手高阶 RAG 都是这个方案。

## Q3：RAG 最容易踩的坑

1. 强制全量检索：闲聊问题也查库，引入噪声
2. Chunk 大小不合理：太长信息混杂，太短上下文断裂
3. Embedding 前后不统一（入库和检索不是同一个模型，完全匹配不到）
4. 只做向量检索不加 Rerank，大量无关文档进入 Prompt
5. Prompt 没做好约束，大模型无视检索资料，胡乱编造（幻觉）
